# VPN Runtime

## Purpose

`vpn-runtime` owns protocol-specific VPN configuration validation, tunnel process lifecycle, fail-closed SOCKS5 egress, readiness, reconnect, prepared activation, bounded clean shutdown, and the stable fail-closed proxy implementation used to switch exact gateway generations. It is independent from browser automation, concrete workflows, and `WorkflowRun` lifecycle.

`workflow-control-center` owns Product resources, authorization, publication, active Version, connection slots, queues, Kubernetes topology, stable Service identities, durable desired/applied generations, and orchestration. `browser-runtime` and workflow containers are ordinary consumers of the resulting SOCKS5 URL. VPN health never authorizes this runtime to change, replace, freeze, stop, or report a state transition for a `WorkflowRun`.

## Protocol Boundary

`protocol` is supplied separately from the snapshot and currently accepts only `openvpn`. The snapshot root contains one strict `config.json` whose `config_path` resolves to a local `.ovpn` file. Optional `login` and `password` must occur together. Additional certificate and key files may exist only inside the same immutable root.

Validation fingerprints the complete tree without following symlinks. It rejects absolute paths, traversal, special filesystem objects, external `auth-user-pass` paths, executable hooks, plugins, management endpoints, provider-owned log paths, unsupported inline blocks, and invalid `remote` host tokens. A valid `remote` may use a hostname or literal IP address. Runtime rechecks the fingerprint, resolves every source hostname with the standard container resolver before each provider attempt, copies the tree into one attempt-local private directory, writes selected IP addresses and contained references only into that copy, creates generated credential files with mode `0600`, and deletes the whole generation after stop. The immutable source hostname is never rewritten. Successive attempts repeat DNS resolution and rotate multiple current addresses.

Each future protocol is a separate adapter behind the same validated gateway lifecycle. A protocol is not accepted merely because Gluetun supports it; the platform contract, parser, security policy, real validation, and cleanup proof must all exist first.

## Gateway Boundary

The final image tracks Python `3.14` patch updates on the Alpine `3.22` branch and pins the multi-platform Gluetun `v3.41.1` OCI index digest, Dante server `1.4.4-r0`, and dnsmasq `2.91-r1`. The adapter supplies one transformed custom-provider configuration, explicit `PUID=0` and `PGID=0`, and only path-valued `OPENVPN_USER_SECRETFILE` and `OPENVPN_PASSWORD_SECRETFILE` settings. Root identity keeps Gluetun's generated OpenVPN configuration and owned authentication link readable across retries without a broad filesystem-override capability; ordinary Dante request handling still drops to the dedicated `vpnproxy` identity and target-DNS forwarding drops to the distinct `vpndns` identity. Raw credentials never enter the child environment. Gluetun's fixed authentication path is an owned link into the current attempt and is removed before the attempt is deleted. Gluetun health/control listeners remain loopback-only and are not stable platform contracts.

Product release разрешает оба поддерживаемых base selector ровно один раз в exact digest целевой platform. Python build/runtime dependencies устанавливаются только из committed hash-locked requirements; Dockerfile не содержит неявного base-image default или незаблокированного разрешения Python dependency.

One gateway owns one tunnel, one tunnel-bound target-DNS forwarder, and one TCP SOCKS5 listener. The standard container resolver remains installed and its exact nameserver IPs receive bootstrap egress through the ordinary interface; runtime control traffic and OpenVPN remote lookup use this resolver independently of tunnel health. Dante's external interface is exactly `tun0`. Firewall rules scoped to UID `vpnproxy` translate only TCP and UDP port-53 requests to the local dnsmasq listener, and dnsmasq binds every upstream resolver socket explicitly to `tun0`. The forwarder does not read the standard resolver, and neither target connections nor target DNS can fall back to the ordinary interface. The container receives `/dev/net/tun` and only `CHOWN`, `KILL`, `NET_ADMIN`, `NET_RAW`, `SETGID` and `SETUID`; `NET_RAW` is required by dnsmasq for interface-bound upstream sockets, while `KILL` lets the owning supervisor stop its own dnsmasq and Dante children after they drop to their isolated UIDs. Readiness is true only when the current fenced generation has an established tunnel, an accepting target-DNS forwarder, installed UID-scoped rules, and an accepting SOCKS listener.

Provider reconnect is one local lifecycle. The listener identity remains stable inside one generation, target egress stays blocked, and readiness is false until recovery. Gluetun may first recover its current connection locally for the immutable `provider_recovery_grace_seconds` of the selected Version. Failure of either dnsmasq or Dante first stops the complete user plane and only then replaces both children, so one generation never owns duplicate listeners. Provider-process exit or grace expiry causes the runtime to stop user egress, bounded-stop the owned provider attempt, repeat standard-DNS resolution, and restore dnsmasq and Dante only after a new private attempt reaches readiness in the same Pod. The Pod is replaced only after supervisor/control failure, Pod loss, or unproved process cleanup. The runtime does not select another Version or interact with workflow/browser processes.

Each exact Version supplies three concrete non-null positive timeouts inside platform-declared safety ranges. `connection_attempt_timeout_seconds` is one monotonic outer deadline from provider-process start through Gluetun, tunnel-bound DNS, SOCKS, and readiness; it does not reset between phases and excludes Kubernetes scheduling/image pull. `provider_recovery_grace_seconds` owns the internal Gluetun recovery window described above. `process_stop_timeout_seconds` is one common graceful deadline for all owned process groups: send `SIGTERM`, wait for groups in parallel, send `SIGKILL` to remaining groups, and perform bounded exit proof without an unbounded `wait()`. Kubernetes termination grace is derived from this deadline plus an explicit supervisor cleanup margin. Allowed native OpenVPN timing directives remain unchanged in the private source-derived configuration but operate inside the outer deadline. Final range limits are accepted with the defaults after real target ARM64 failure/stop measurements and a maximum resource-ownership review; unbounded values are invalid.

The platform-owned health observation interval is 5 seconds and is not a publisher timeout or retry delay. Gateway mode retries transient provider attempts indefinitely in the same Pod with exponential backoff from 1 to 300 seconds. Validation mode executes one bounded lifecycle and returns a structured success, deterministic failure, or transient failure so WCC can clean up, release the slot, wait without a reservation, and re-enter its fair queue. Baseline Version defaults are `180`, `180`, and `30` seconds. Final defaults may only increase after repeated real ARM64/k3s `/dev/net/tun` measurements with the pinned Gluetun image show a higher observed maximum plus margin.

## Stable Proxy Boundary

One run/config proxy has a stable listener whose address contains neither Version nor generation. It is built as a separate minimal OCI image target that contains no Gluetun, OpenVPN, Dante, dnsmasq, gateway capabilities, or privileged gateway entrypoint. It receives no VPN configuration, credentials, `/dev/net/tun`, AWS identity, Kubernetes token, or default/direct upstream and runs as a non-root process with a read-only root filesystem, all capabilities dropped, and `RuntimeDefault` seccomp. Network policy permits exact run consumers to reach it and permits it to reach only the exact selected gateway upstream.

The proxy exposes only a private mode-`0600` generation-fenced Unix control socket with `disable`, exact-upstream mutation, and status. Every process start generates a new non-secret random runtime instance identity and starts disabled, including a container restart inside the same Pod. The daemon reads its own Pod UID through the Downward API; every mutation carries exact expected Pod UID, runtime instance identity, and generation and is rejected on mismatch. Disable is fail closed. Set-upstream becomes visible atomically only after the orchestrator has proved the target gateway ready; a smaller generation is rejected and an equal generation is idempotent only for that same runtime instance. Raw HAProxy or another component's runtime API is never exposed. `workflow-control-center` checks UID/status before and after mutation, persists desired/applied generation bound to exact `(Pod UID, runtime instance identity)`, and owns generation-local egress policy. Lifecycle revocation independently removes every proxy-to-gateway policy and sends disable, so failure of one boundary cannot preserve a usable upstream; this repository owns the safe proxy behavior only.

## Prepared Activation And Fencing

A replacement gateway Pod starts in prepared state after static validation but without opening a provider connection. Optional standard-DNS prefetch may warm local state but is not provider-attempt identity; `activate` performs the authoritative fresh lookup immediately before provider-process start. The image runs a minimal daemon with a mode-`0600` local Unix socket, atomic redacted status file, and shell-free control CLI. Platform `pods/exec` commands `activate <generation>`, `status <generation>`, and `stop <generation>` are idempotent for the same generation and reject smaller generations. The durable highest generation is restored as prepared rather than falsely restoring process readiness. The controller verifies exact Pod UID before every command.

Activation starts the exact validated snapshot and publishes readiness only after tunnel and SOCKS checks. Stop prevents new target work, closes the provider connection, proves owned child processes exited, and leaves no reusable credential file. The runtime does not decide when Service selectors change or when old Pods are deleted.

## Validation Boundary

The validation runner and production gateway for one `VpnConfigVersion` use the same exact pinned gateway image digest, parser, adapter, Gluetun digest, SOCKS implementation, timing contract, and security configuration. One validation Job executes one bounded lifecycle and never enters the gateway's indefinite reconnect loop. Platform-owned fixtures provide one private random S3 nonce through a bounded presigned HTTPS GET URL mounted from a Kubernetes Secret file. Validation proves strict parsing, real connection, proxy-side DNS, tunnel egress by exact nonce bytes, fail-closed behavior, and bounded clean shutdown. It receives no AWS credentials and records no exit IP. URL/nonce values never enter arguments, logs, status, or report; WCC owns renewable-signing-session proof, object/Secret cleanup, fair retry after transient failure, and the one-day abandoned-object lifecycle.

Infrastructure failures are distinguishable from deterministic config/test failures through structured phases and diagnostics. Retry policy and `VpnConfigVersion` state transitions belong to `workflow-control-center`.

## Security Boundary

The gateway receives only the exact immutable snapshot and private runtime storage. It does not receive Product DB, S3, KMS, registry, Kubernetes API, browser profile, workflow input, or other users' configurations. Only the gateway container receives `/dev/net/tun` and the minimum network capability required by the protocol.

Logs, health, validation reports, and process errors redact configuration bodies, credentials, private keys, generated authentication files, and provider tokens. There is no user-facing or cluster-public management API.

## Verification Contract

Unit tests cover strict config shape, path containment, symlink and directive rejection, hostname acceptance, attempt-local IP rendering, repeated resolution, standard resolver preservation, UID-scoped DNS rules, credential pairing, generated-file permissions, monotonic attempt/recovery/stop deadlines and bounds, parallel process-group cleanup, bounded forced-stop proof, retry backoff, gateway generation fencing, restart-disabled stable-proxy fail-closed switching, readiness state, and redaction. Container integration tests use real `/dev/net/tun` and valid OpenVPN credentials to prove standard-DNS hostname bootstrap, tunnel establishment, exact private nonce access by hostname through SOCKS5, proxy-side DNS through `tun0`, ordinary system DNS outside the tunnel, fail-closed behavior during tunnel loss, same-Pod fresh provider-attempt recovery, authoritative activation-time lookup after prepared wait, stable proxy atomic switch/restart, and bounded graceful/forced shutdown. Repeated measurements run on the target ARM64 k3s environment and cover cold/warm activation, DNS change, blackhole/recovery, unreachable provider, invalid authentication, attempt replacement, and stop margins. Kubernetes integration in `workflow-control-center` owns slot accounting, stable Service identity, surge/no-spare reservation orchestration, active-Version rotation, initial all-proxy admission, and proof that later VPN state does not change `WorkflowRun` lifecycle.
